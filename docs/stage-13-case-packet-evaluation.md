# Stage 13: paired case-preparation development evaluation

The repository now has an automatic comparison of the production template-only
packet workflow and the same workflow with optional model interpretation. It uses
no wallet, database, merchant or chain calls. The model arm calls only local Ollama.
This is an author-labelled synthetic development evaluation, not an independently
reviewed held-out benchmark or a human productivity study.

## What is compared

Twelve newly written cases cover direct complaints, paraphrases, negation,
hypotheticals, resolved history, retraction, mixed negation and access failure,
unclear concerns, embedded instructions, and a claim with an existing local refund
record. They are separate from the three Stage 10 smoke inputs. The test checks
that separation; it does not establish broader dataset independence.

Both arms call the real `assembleCasePacket` implementation on identical synthetic
local snapshots. The model uses the unchanged production `interpretPacketClaims`
adapter and receives only source IDs and party text. Case identifiers, strata,
expected topics, annotations and synthetic ledger data are never in the model's
input. The production backend still assembles facts deterministically.

Three results are kept distinct:

- **Template workflow:** rule topics and their generated follow-up questions.
- **Model alone:** accepted interpretations, with exact source quotes and their
  annotation-based support checks. Rejected/unavailable attempts receive no score
  and remain in the attempt denominator, including negative cases.
- **Assisted workflow:** the actual production union of rule and model topics,
  followed by the production question generator. A rule fallback after model
  failure is a workflow outcome, never reported as model success.

The union is consequential: even a model that correctly recognizes a retracted
claim cannot remove a rule false positive. Tests demonstrate this explicitly.

## Scoring boundaries

Exact topic-set matching compares unique current-topic categories. Minimum topic
set edits count missing plus extra topics; this is a theoretical correction lower
bound, not measured operator edits or time. Material coverage compares required
follow-up question categories (charge references, reproduction, refund linkage,
clarification); it does not certify completeness of all information in a document.

A candidate is annotation-supported only if its quote exists in the actual source
and contains an annotated supporting span for the same topic and source ID. Exact
quotation alone does not prove correct interpretation. Distinct topic/source/quote
triples are deduplicated regardless of JSON property order. Different quotes for
the same topic can still produce multiple candidates; candidate counts are not
counts of distinct incidents. Annotation support is provisional semantic evidence,
not independent ground truth or financial verification.

No unconstrained model-written financial statements are generated by this workflow.
`deterministicFactsUnchanged` checks that the two arms retain identical record facts;
it does not prove those synthetic records describe a real-world payment correctly.

## Captured local run

The [paired report](evidence/stage-13-case-packets-3b.json),
[pre-run manifest](evidence/stage-13-case-packets-3b.json.plan.json) and
[per-case journal](evidence/stage-13-case-packets-3b.json.cases.jsonl) preserve the
actual local `qwen2.5:3b` run. No prompt, model or case tuning was performed after
seeing this run. Total model call time was about **28.9 seconds**; this is not
human work time, a latency SLA or a cost saving.

| Metric, 12 synthetic cases | Template | Template + model |
| --- | ---: | ---: |
| Exact topic sets | 4/12 | 5/12 |
| Exact required question-category sets | 5/12 | 5/12 |
| Missing question categories | 4 | 2 |
| Unnecessary question categories | 9 | 10 |
| Minimum topic-set edits | 13 | 12 |
| Unsupported quoted candidates / all candidates | 8/13 | 15/23 |

All twelve model responses passed the shape/quote gate. Model-alone exact topic
matching was **5/12** and exact matching with every candidate annotation-supported
was **4/12**. Passing the structural gate therefore did not establish semantic
accuracy. The assisted workflow improved topic-set edit distance on one case and
worsened it on two; deterministic record facts stayed unchanged on all twelve.

Notable failures include treating explicit denial and resolved allegations as
current complaints, inventing a refund topic from a hypothetical support question,
and classifying an embedded payout instruction as a refund claim. The paraphrase
case improved by recovering three topics missed by the keywords. These observations
do not justify promoting the model or claiming stable operational value. Model
interpretation remains disabled by default.

## Reproduce or review

The captured results below belong to protocol v1 at commit `ddebe79`. After
[Stage 14](stage-14-case-packet-context.md), current CLI runs use v2 context review
and separately report held cases. Old reports remain unchanged; current runs are
not exact re-executions of the v1 workflow.

Use a new output filename. Existing files are never overwritten.

```sh
# No model or network required.
npm run --silent eval:case-packets -- --rules-only --output /tmp/case-packets-rules-new.json

# Requires this model to be installed in local Ollama; does not download models.
npm run --silent eval:case-packets -- --model qwen2.5:3b --output /tmp/case-packets-3b-new.json

# Exports inputs and blank annotations, without author labels or model answers.
npm run --silent eval:case-packets -- --export-review --output /tmp/case-packets-review-new.json
```

A [blank review form](evidence/stage-13-case-packet-review-form.json) is included.
It is a reviewer handoff artifact, not a completed independent review. The scorer
currently uses the author labels in source; it does not import arbitrary completed
forms or claim reviewer agreement automatically.

The runner pins the dataset digest, Node version, recursive source/compiled-module
hashes, lockfile and local model digest. It verifies sources before execution and
model identity before every case and after the run. Cases execute serially, with
production timeouts and response limits. Each completed case is flushed to a
sidecar journal. A failed or interrupted run can leave a reserved empty final file
and partial sidecars; only a complete final report with `finishedAt` is a completed
run. Do not silently treat partial journals as successful evaluation results.

## Verification and next step

`npm test`: **244/244 passed**, no skips, about 31.7 seconds excluding build.
Tests cover source-bound annotations, old-smoke separation, blank review export,
input/label isolation, unsupported quotes, duplicate scoring, failure denominators,
production union behavior, per-case capture and pre-inference identity rejection.
Existing frozen evaluation and financial safety checks remain passing.

No database migration, service restart or payment was performed. The next change
should address assertion context and conflicting candidates before enlarging the
model or claiming ROI: retain the original evidence, flag denial/retraction/quoted
instructions for review, and avoid silently treating every keyword or model topic
as a current complaint. Any development against these observed examples must be
labelled as development; independent labels and new held-out cases are still needed
before a generalization or human-efficiency claim.
